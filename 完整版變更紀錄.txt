----------------------------------------------------------------
1. 使用者確認 v1.9.69 的標籤偵測「只看標籤」不夠用，要求再加兩種判斷依據：「同一位地主當過去已經寄過信（不同地號/持分，只要同一個人就算）」跟「同一地址寄過（避免同一個信箱重複收到兩封）」。

2026-09-03 家中伺服器 v1.9.40 修正真正的根本原因：「標記已匯出」在 PostgreSQL 上每次都靜默失敗
----------------------------------------------------------------
1. 承接 v1.9.68 的診斷紀錄——使用者更新後重新測試（連單筆資料都測過），`application-error.log` 裡完全沒有任何例外紀錄，代表問題不是「例外被吞掉」，而是更底層的邏輯本身有誤。
2. 追查出真正原因：家中伺服器用的 PostgreSQL 驅動（psycopg 3）的「連線物件」（Connection）**根本沒有 `executemany` 這個方法**，只有從它另外開出來的「游標」（Cursor）才有。v1.9.39 新增「標記已匯出」功能時，直接對連線物件呼叫了 `executemany`，在真正的 PostgreSQL 伺服器上每次都會丟出 `AttributeError`——但因為桌面端的容錯設計刻意把這類查詢/標記失敗視為「不要卡住使用者的匯出」而靜默略過（且伺服器端的例外是記錄到伺服器自己的錯誤紀錄檔，不是桌面端的 `application-error.log`，才會完全查不到蛛絲馬跡），導致每次「標記已匯出」實際上都沒有真的寫進資料庫。
3. 這個系統其實**早就在另一個既有功能（修改歷史批次寫入）遇過同一種錯誤，也早就寫好了正確的解法**（透過真正的游標執行批次，而不是連線物件本身）——這次新增功能時沒有重複使用那個既有的正確寫法，才踩到這個坑。
4. 修正：「標記已匯出」改用正確的游標批次寫入方式，跟系統裡其他 PostgreSQL 批次寫入功能用同一套寫法。
5. 新增測試：用一個「刻意模擬 psycopg 3、沒有 executemany」的假連線物件，鎖定這個問題以後不會再發生（如果哪天不小心又寫成呼叫連線物件的 executemany，這個測試會直接失敗）。本機測試 501 個全數通過。
6. **這次確認是伺服器端獨有的問題**（本機獨立模式用的是 SQLite，SQLite 的連線物件本來就有 executemany，不受影響，難怪一開始很難查——同一段程式碼邏輯在本機模式完全正常，只有連線家中伺服器模式才會出錯），純伺服器端修正，公司筆電客戶端不需要更新。
7. 麻煩更新家中伺服器後，重新測試一次「匯出同一筆資料兩次」，確認第二次會正確跳出重複提示。

2026-09-03 公司筆電 v1.9.66 修正：匯出 Excel 後程式沒回應，而且重複匯出偵測不出來
----------------------------------------------------------------
1. 使用者回報：按下匯出後，就算是重複匯出的資料也不會跳出剛新增的重複提示，而且**程式整個沒回應**（畫面截圖顯示 Windows 標題列出現「(沒有回應)」，跳出的「匯出完成」訊息框內容整個空白）。
2. 追查根本原因：v1.9.64 新增「標記已匯出」功能時，把「匯出完成後要做的事」（標記已匯出＋跳出完成訊息）包在一個普通的 Python 函式（closure）裡，直接傳給背景執行緒的完成訊號。Qt 只有在收訊號的對象是「真正掛在物件上的方法」時，才能正確判斷這個方法該在哪個執行緒執行、自動轉成安全的跨執行緒呼叫；普通函式沒有這種歸屬資訊，導致這段程式碼**直接在背景執行緒上執行**，而不是切回主畫面執行緒——包含裡面要跳出的「匯出完成」訊息框，這在 Qt 是未定義行為，實際表現就是畫面凍結、內容空白、Windows 判定程式沒回應。這正是這個系統之前已經在別的功能上踩過、並且明確記錄下來要避免的同一種錯誤（背景執行緒直接碰觸只能給主畫面用的東西）。
3. 這也連帶說明了「重複匯出偵測不出來」：因為標記已匯出的資料庫寫入動作本身也是在背景執行緒上跑的，沒有可靠地真正完成，下次匯出時系統當然查不到「這筆之前匯出過」的紀錄。
4. 修正：把「匯出完成後要做的事」改回一個真正掛在主畫面物件上的方法（跟這個系統其他背景工作已經在用的安全寫法完全一致），讓 Qt 能正確判斷要切回主畫面執行緒執行，徹底解決凍結問題，標記已匯出的動作也能可靠地真正寫入。
5. 新增回歸測試，直接鎖定「傳給背景工作的完成處理函式，必須是真正掛在物件上的方法，不能是普通函式」這個規則，避免未來又不小心用回錯誤寫法。本機測試 498 個全數通過。
6. 純客戶端調整（`customer_export_controller.py`），家中伺服器不用升級。
7. 麻煩更新後**實際重新測試看看「匯出 Excel」跟重複匯出偵測功能**，確認畫面不會再凍結、重複偵測也正常跳出。

----------------------------------------------------------------

2. 追查根本原因：這個系統在「連線家中伺服器」模式（API 模式）下，每次登入都會**刻意產生一組全新的隨機加密金鑰**（`configure_api_authentication()`，這是既有設計，因為 API 模式的資料本來就已經是伺服器解密好傳過來的，這組隨機金鑰只是給桌面畫面內部表單流程用的臨時工具，本來就不需要固定）。但 v1.9.60 把 Google API 金鑰用「目前登入的加密金鑰」加密後存起來——這在本機獨立模式沒問題（金鑰是從密碼算出來的，每次登入都一樣），但在連線家中伺服器模式下，這組加密金鑰每次登入都不一樣，上一次存的金鑰下一次登入時完全無法解密，只能默默當作「沒有設定」處理，等於金鑰永遠存不住。
3. 修正：Google API 金鑰改成**用純文字直接存**，不再用登入金鑰加密——這跟系統裡其他本機專屬設定（例如伺服器網址、字體大小、常用搜尋條件）本來就是同樣的存法。這把金鑰只會留在你這台電腦本機的設定檔裡，不會傳到任何地方，加上原本設定時就已經限制只能用來查詢地理編碼（Geocoding API），風險跟目前系統裡其他本機設定是同一個等級。
4. 新增回歸測試：模擬「用不同的加密金鑰重新打開對話框」（等同連線伺服器模式下兩次不同的登入），確認金鑰真的能正確保留下來。本機測試 489 個全數通過。

2026-08-17 公司筆電 v1.9.29 表格模型崩潰修正（根治，已回退，見上方 v1.9.30）
----------------------------------------------------------------
1. 部署 v1.9.28 後回報仍會崩潰，但這次的 log 給出了關鍵線索：崩潰確實是先進到新增的 `_node_for_index()` 防呆檢查（log 看得到 `File "customer_models.py", line 163, in _node_for_index`），代表拿到的物件通過了 `isinstance(node, _TreeNode)` 判斷，卻仍在存取 `.kind` 時丟出 `AttributeError`。`_TreeNode` 的 `kind` 是建構子唯一必填、之後不會被改寫的欄位，isinstance 通過卻讀不到，代表問題不是「型別不對」，是更根本的層次。
2. 真正原因：`RecordTableModel` 一直把 `_TreeNode` 物件本身當成 `createIndex(row, column, node)` 的第三個參數，交給 Qt／PySide6 底層當內部指標存放。這是 PySide6 官方文件明確提醒過的脆弱寫法——用 Python 物件當內部指標，其存活期完全依賴 shiboken 的包裝機制，在 `beginResetModel()`／`endResetModel()` 把節點整批換掉、又有 QModelIndex 在事件佇列或畫面元件內部快取裡存活得比預期久時，指標解回來的物件不保證是原本那個、也不保證有正確初始化——這正好解釋了「型別是 `_TreeNode` 沒錯，但關鍵欄位讀不到」這個奇怪的症狀。
3. 改用 Qt 自己文件建議的標準做法：`createIndex()` 一律只帶一個單純的整數 `node_id`，不再傳遞 Python 物件；新增 `self._nodes_by_id`，是模型自己完全掌控的「編號→節點」字典，每次 `_rebuild_nodes()` 都整份清空重建，`node_id` 只增不減、永不重複使用。解析索引時改用 `index.internalId()` 查這個字典，查不到就回傳 None——舊編號在重建後必然查不到，從架構上排除了「解到壞掉物件」的可能性，不再只是事後攔截症狀。
4. 新增測試直接模擬正式環境的情境：先取得一個有效索引，讓模型重建成不同資料，驗證舊索引安全降級、且新舊索引的 `internalId()` 保證不同——證明不會有編號被誤用到別的節點上。

- 在載入 openpyxl 前補齊 openpyxl 會使用的 NumPy 型別別名
- 若環境沒有 NumPy，仍維持原本不依賴 NumPy 的處理方式

4. 測試：
- 新增「打包環境 NumPy 缺少 short 別名」回歸測試

四十二、v1.1.3 進階搜尋同欄多值

1. 欄內任一符合。
- 同一進階搜尋欄位可用「、」、「，」或半形逗號分隔多個值
- 每個值會個別正規化、忽略空白並自動排除重複條件
- 例如地段輸入「中路、中路段」會找出包含中路或中路段的資料

2. 欄間全部符合。
- 不同欄位仍以 AND 組合，避免放寬原有多條件篩選
- 例如地區填桃園區且地段填「中路、中路段」，只顯示桃園區內符合任一地段的資料

3. 全路徑一致與介面提示。
- SQLite 候選查詢會為每個欄位建立 OR 群組，再以 AND 串接不同欄位
- 解密後敏感欄位比對與 FastAPI 資料篩選套用相同規則
- 進階搜尋視窗的說明與欄位提示會直接顯示可用分隔符號

4. 驗證。
- 新增欄內多值解析、資料庫 OR、解密後 OR、API OR 及介面提示測試
- 單元與整合測試共 140 項通過
