# 土地資料系統：專案現況與討論事項

> 整理日期：2026-10-20。給「要和 Claude 討論這個專案」時當背景資料用。
> 內容只寫我實際查證過的事；不確定的地方會標「推測」。不含任何密碼、連線字串或客戶個資。

## 1. 這個系統是做什麼的

給一個人（加上少數同事）管理**土地與地主資料**用：登記哪些地號、面積、公告現值、有哪些所有權人與持分，並記錄拜訪、聯絡、追蹤、附件。資料量目前約 **696 筆土地、2,236 筆所有權人持分**，不大，但資料敏感（姓名、身分證、地址、備註）。

主要使用情境：

- 公司筆電用桌面程式，透過 NetBird VPN 連回家裡的伺服器。
- 外出拜訪用手機網頁（PWA），看路線、導航、記錄拜訪結果。
- 偶爾用 Excel 整批匯入、匯出。

## 2. 架構

| 部分 | 技術 | 備註 |
|---|---|---|
| 家中伺服器 | Python FastAPI + PostgreSQL 18，PyInstaller 打包成 exe | 路由在 `customer_api/`，資料結構在 `postgres/schema.sql`，啟動時自動、可重複套用升級 |
| 伺服器控制台 | tkinter + Pillow（原生 tk，刻意不用 customtkinter，因為啟動要 8–12 秒） | `server_console/`，管理啟停、備份、帳號 |
| 公司筆電客戶端 | PySide6（Qt）桌面程式 | 連伺服器走 HTTPS，客戶端自己信任伺服器產生的本機 CA |
| 手機外勤 | `customer_mobile_web/`，PWA | 路線規劃、Google 地圖導航、拜訪紀錄 |
| 單機版 | 同一套桌面程式 + SQLite | 保留著，但實際使用以連伺服器為主 |

資料模型（PostgreSQL）：土地 `lands` ← 持分 `ownerships` → 所有權人 `owners`；另有聯絡紀錄、追蹤提醒、案件、標籤、附件、關係人、外勤路線等。

**加密**：姓名、身分證、地址、備註、出訪記錄、出生年用 Fernet 加密後才寫進資料庫，金鑰由使用者密碼保護。檢視者角色看到的身分證是遮罩後的。**面積、公告現值這類土地欄位不加密。**

**權限**：admin / editor / viewer，唯讀帳號所有寫入 API 都回 403。

## 4. 最近完成的主要工作

### 4.1 「都市計畫」分類（2026-10-03，commit `185d48c`）

需求：依「都市計畫」（例如龍岡都市計畫）分類土地與地主，再細分地段。

清單階層：**都市計畫 → 地段 → 小段 → 地號 → 地主**。

設計決定：

- 都市計畫是**土地**的屬性，一塊土地只能屬於一個計畫，同一塊土地上的所有地主跟著歸類。沒歸類的叫「未分類」。
- 先在「都市計畫管理」建立名單（新增、改名、刪除）。刪除計畫只會讓它的土地回到未分類，**不刪任何土地或地主**。
- 資料輸入時歸類：工具列「輸入到」決定新資料與匯入 Excel 的預設計畫；既有資料用「設定都市計畫」整批歸類（預設只動未分類的土地）。
- 匯入**不覆蓋**已經屬於其他計畫的土地，匯入完成後列出那些沒變更的土地，可匯出。
- 工具列「檢視」可選：依土地（舊）／全部都市計畫／某一個計畫／未分類。只選一個計畫時清單只顯示它。
- 只做在桌面清單，**沒有**做到手機網頁、Excel 匯出欄位。

實作上的取捨：

- 舊的土地樹狀清單的 Model（`RecordTableModel`）有很長的當機歷史，所以**完全不動它**，另外做一個新的清單元件，兩者用堆疊視窗切換。舊樹仍是資料、選取、儲存的依據。
- 資料庫新增 `urban_plans` 表與 `lands.urban_plan_id`（`ON DELETE SET NULL`），附獨立的還原腳本。
- 儲存時只有「真的改了都市計畫」才送出這個欄位，所以新客戶端連舊伺服器、舊客戶端連新伺服器都能正常用。
- 既有的 `lands.zoning` 欄位沒用到，保留給之後的「使用分區」。

驗證過的：新 SQL 在真實 PostgreSQL 的暫時 schema 跑過 32 項行為檢查；2,236 筆資料下重建清單約 0.18 秒。

## 5. 2026-10-07 的 Excel 匯入問題（已結案）

使用者回報匯入 .xlsx 時「面積、公告現值、備註沒有跟著匯入」。我用真實檔案走完整條路（讀 Excel → 客戶端 → API → PostgreSQL → 讀回）都正常，最後使用者確認**是 Excel 表頭沒設定好**。

這件事暴露的幾個設計問題，可以討論：

1. **表頭認不得時完全沒有警告。** 欄位對應不到就整欄默默略過，使用者只能自己看「對應欄位」那一行。
2. **「略過重複後匯入」不會補欄位。** 資料庫已有這個人、新檔案多了面積／備註時，要選「更新既有並匯入」才會補，這個差別在畫面上不明顯。
3. **重複判斷依賴身分證與序號。** 新檔案如果沒有身分證欄，系統認不出是同一人，會多建一批新的所有權人，而不是更新原本那批。我用兩份真實檔案試過：1,619 筆再匯 690 筆，變成 2,309 筆。

## 7. 已知風險與技術債（我的判斷，供討論）

1. **備份**：2026-09 的資料庫被清空事件中，附件、案件歷史、標籤、操作紀錄**確認無法還原，因為當時沒有真正的備份**。程式裡有備份功能與異地備份目標，但我不確定現在有沒有人定期做、有沒有試過還原。這是我認為**最值得優先確認**的一項。
2. **桌面清單的穩定性**：土地樹狀清單 Model 過去因為執行緒、重建時機等問題有過多次原生當機（存取違規，Python 抓不到）。現在靠一堆「不要同步重建」「背景搜尋要排隊」的規則撐著，新增功能時我選擇繞開它而不是改它。
3. **伺服器列表效能**：`list_records` 每一頁都把全部資料撈出並解密後才切頁，下載全部資料的成本隨筆數平方成長。目前 2,000 多筆還能忍，筆數再成長會變慢（客戶端已做了快取緩解）。
4. **發行流程偏手工**：伺服器 exe 的 PyInstaller 設定檔沒進版本控制、含絕對路徑；這次我是用暫時的乾淨工作樹手動組出來的。正式的 `build_postgresql_release.py` 需要驗收報告才能跑，這次沒走那條路。
5. **單人維護**：沒有第二個人能接手時的文件，目前只有變更紀錄和少量說明。

## 8. 想跟 Claude 討論的問題

按我覺得的優先順序：

1. **備份與還原**：怎麼設計一個不依賴人記得的備份（頻率、位置、定期自動驗證能還原）？現有的備份功能夠不夠？
2. **Excel 匯入怎麼讓人不會設定錯**：表頭認不得要不要擋下來或警告？重複判斷要不要改成用「地段＋地號＋姓名」這類較寬鬆的條件？「略過」與「更新」兩個按鈕怎麼說明才清楚？
3. **都市計畫的下一步**：
   - 要不要支援 Excel 內直接帶「都市計畫」欄位，一次匯入就分好類？
   - 手機網頁與匯出需不需要看得到都市計畫？
   - 「使用分區」（住宅區、商業區…）和「都市計畫」是不同概念，要不要用另一個欄位處理？（目前 `lands.zoning` 空著）
   - 面積、公告現值、使用分區能不能從公開資料自動帶入，而不是人工維護？
4. **筆數成長後的效能**：伺服器列表要不要改成真正的分頁與查詢下推到資料庫，代價是什麼（加密欄位不能直接在 SQL 搜尋）？
5. **版本與發行**：怎麼把「從乾淨的 commit 打出客戶端＋伺服器發行包」變成一個腳本，不再靠手動？版號規則要不要統一？
6. **桌面清單的長期方向**：繼續維持舊 Model 加外掛，還是找時間用較簡單的結構重寫？重寫風險與收益怎麼估？
